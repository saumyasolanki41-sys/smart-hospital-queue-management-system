# Visit history feedback and queue pause

Implemented in the local backend. Push and deploy the revision before using these
routes on the shared backend. The earlier Word proposal is planning material;
this document is the implementation contract. No frontend/mobile screens have
been added in this backend checkout.

Import [the Postman collection](visit-features.postman_collection.json), set its
baseUrl, patientToken, staffToken, doctorId and tokenId variables privately, and
exercise the five new endpoints. Use the linked doctor's access token or an
admin/receptionist token as staffToken.

## New endpoints

| Method | Path | Allowed roles | Success |
| --- | --- | --- | --- |
| GET | `/api/queue/history` | patient | 200 |
| GET | `/api/queue/tokens/:id/feedback` | owning patient | 200 |
| POST | `/api/queue/tokens/:id/feedback` | owning patient | 201 |
| PATCH | `/api/staff/queues/doctors/:doctorId/pause` | linked doctor, admin, receptionist | 200 |
| PATCH | `/api/staff/queues/doctors/:doctorId/resume` | linked doctor, admin, receptionist | 200 |

All routes require `Authorization: Bearer BACKEND_ACCESS_TOKEN`. Send JSON bodies
with `Content-Type: application/json`. Patients cannot manage pause state. Doctor
accounts cannot manage a different doctor's queue. Role middleware still applies;
an admin cannot use patient-only history/feedback routes to inspect other patients.
The backend now defines 42 method-and-route endpoints, up from 37.

## Patient visit history

```http
GET /api/queue/history?status=completed&page=1&limit=20
```

Optional filters: `from` and `to` are inclusive queue dates in real `YYYY-MM-DD`
format. Dates refer to India's queue calendar, not a completion timestamp filter.
An inverted range is rejected. With no dates, history spans all stored dates.

- `status`: defaults to `completed`; accepts `all`, `waiting`, `called`,
  `completed`, `cancelled`, `skipped`.
- `page`: defaults to 1; maximum 100000.
- `limit`: defaults to 20; maximum 50.
- Unknown fields, arrays, invalid values and arbitrary `patientId` are rejected.

Only the logged-in patient's records are selected, sorted by queue date, creation
time and ID descending. Empty results return 200 with `visits: []` and `total: 0`.
Feedback is included only where it exists. Records remain after completion,
cancellation and skipping. This is administrative visit history, not diagnoses,
prescriptions or a medical record.

Illustrative response:

```json
{
  "success": true,
  "data": {
    "visits": [{
      "_id": "TOKEN_ID",
      "doctor": {
        "_id": "DOCTOR_ID",
        "name": "Example Doctor",
        "specialization": "Cardiologist",
        "department": {"_id": "DEPARTMENT_ID", "name": "Cardiology"}
      },
      "queueDate": "2026-11-10",
      "tokenNumber": 3,
      "status": "completed",
      "completedAt": "2026-11-10T08:00:00.000Z"
    }],
    "total": 1,
    "page": 1,
    "limit": 20
  }
}
```

Doctor and department references can be null if removed through direct database
administration. Render unavailable labels safely. History does not calculate
waiting time or call ML. Existing `/tokens/mine` remains a same-day/date-filtered
list; it is not changed into a history endpoint.

## Feedback after consultation

```http
POST /api/queue/tokens/ACTUAL_TOKEN_ID/feedback
```

```json
{"rating": 4, "comment": "Helpful consultation."}
```

`rating` is a JSON integer from 1 to 5. Numeric strings and fractional values are
invalid. `comment` is optional, trimmed, at most 1000 characters after trimming.
No extra fields are accepted. Submission time is generated by the backend.

The token must belong to the patient and be `completed`. A token can receive
feedback exactly once; the atomic update prevents concurrent requests from
overwriting it. There is no edit/delete API in this version. Inform the patient
before submission that feedback is final.

```json
{
  "success": true,
  "data": {
    "tokenId": "TOKEN_ID",
    "feedback": {
      "rating": 4,
      "comment": "Helpful consultation.",
      "submittedAt": "2026-11-11T08:00:00.000Z"
    }
  }
}
```

GET the same path to retrieve saved feedback. Before submission it returns
`data: { tokenId: "TOKEN_ID", feedback: null }`. Missing and other patients'
tokens both return 404. Existing token list/status responses now also select the
optional feedback field. Old tokens need no backfill.

Feedback is stored as an optional subdocument on the queue token. It is private
to the owner through these APIs: no public ratings, doctor ranking, or staff
review endpoint was added. Clients must render comments as plain text and should
ask users not to include medical details. Ratings do not affect queue order,
consultation averages or ML inputs.

## Doctor pause and resume

```http
PATCH /api/staff/queues/doctors/ACTUAL_DOCTOR_ID/pause
```

```json
{"reason": "break"}
```

Only `reason` is accepted: `break` or `temporary_delay`. Free-text reasons are
not accepted, so private medical/staff information is not exposed to patients.

```json
{
  "success": true,
  "data": {
    "doctorId": "DOCTOR_ID",
    "queueState": {
      "paused": true,
      "reason": "break",
      "pausedAt": "2026-11-11T08:00:00.000Z"
    }
  }
}
```

Resume with PATCH `/api/staff/queues/doctors/ACTUAL_DOCTOR_ID/resume` and `{}`
or no body. Response `queueState` becomes:

```json
{"paused": false, "reason": null, "pausedAt": null}
```

Behavior:

- A called consultation must be completed/skipped before pause; otherwise 409
  `QUEUE_BUSY`. Pausing does not interrupt or freeze an ongoing consultation.
- While paused, Call Next returns 409 `QUEUE_PAUSED`.
- Repeating the same pause preserves its original timestamp; repeating resume
  is safe. A different reason while already paused returns 409 `QUEUE_PAUSED`;
  resume first, then pause with the new reason.
- Tokens, numbering and order are preserved. Patients can still cancel waiting
  tokens. New bookings remain allowed when `isAvailable` is true.
- `isAvailable` and pause are separate. Setting availability is not pause/resume.
- Pause persists across midnight and restarts until explicitly resumed. Clients
  should show a prominent paused banner even when there are no tokens today.
- Pause and Call Next both write the same doctor guard within a MongoDB
  transaction. Concurrent calls serialize rather than allowing a paused queue
  and a newly called token together.

## Patient estimates and exposed state

`queueState` is added alongside the existing fields on:

- Token status GET `/api/queue/tokens/:id`.
- Normal successful booking POST `/api/queue/tokens`.
- Staff queue GET `/api/staff/queues/doctors/:doctorId/tokens`.
- Doctor dashboard GET `/api/doctor/dashboard`.

For today's waiting token during pause:

```json
{
  "peopleAhead": 2,
  "estimatedWaitMinutes": null,
  "averageConsultationMinutes": 15,
  "consultationOverdue": null,
  "prediction": {"source": "unavailable", "reason": "queue_paused"},
  "queueState": {
    "paused": true,
    "reason": "break",
    "pausedAt": "2026-11-11T08:00:00.000Z"
  }
}
```

These fields live in `data` next to `data.token`. Waiting count remains available,
but the backend skips ML and does not claim a numeric wait during pause. After
resume, request fresh status for the normal estimate. Non-waiting/historical
tokens still have null waiting metrics. Queue state describes the doctor's
current state, not a historical pause at the time of the visit.

Doctor directory/detail and populated patient-token doctor objects additionally
expose `queuePaused`, `queuePauseReason`, `queuePausedAt`. Treat absent values on
old stored records as unpaused; the normalized `queueState` already does this.
`queueRevision` is an internal guard and is not exposed. Doctor records are not
bulk migrated. For a removed doctor, token-status `queueState` is null.

Existing booking-estimation failure behavior is preserved: the booking stays 201
with its saved token and unavailable metrics. `queueState` is null in that error
fallback, so fetch status again rather than assuming it is unpaused or rebooking.

## Error contract

Errors retain `{ "success": false, "error": { "code": "...", "message": "..." } }`.

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | Invalid input/filter/body |
| 401 | UNAUTHORIZED | Login token missing, invalid or expired |
| 403 | FORBIDDEN | Role/doctor queue access not allowed |
| 404 | TOKEN_NOT_FOUND | Missing/unowned patient token |
| 404 | DOCTOR_NOT_FOUND | Doctor profile missing |
| 409 | VISIT_NOT_COMPLETED | Feedback submitted before completion |
| 409 | FEEDBACK_EXISTS | Feedback already saved |
| 409 | QUEUE_BUSY | Ongoing consultation blocks pause/another call |
| 409 | QUEUE_PAUSED | Call Next blocked or pause reason conflicts |
| 429 | RATE_LIMITED | Request limit reached |

History and feedback reads use the existing 60/minute user status limiter;
feedback submission shares the queue-change limit of 20/15 minutes. Pause/resume
share the staff queue-change limiter. Clients must debounce repeat actions.

## Web and Flutter integration

1. Add Visit History to patient navigation. Default to completed, allow status
   and date filters, and paginate. Do not show live estimates on old visits.
2. On completed visits without feedback, show Leave feedback. Require a star
   selection, optional comment and final-submission notice. On 409 FEEDBACK_EXISTS,
   fetch saved feedback. After an uncertain network result, read before retrying.
3. Add Pause/Resume on doctor/staff queue screens. Disable Call Next while paused.
   If a token is called, complete/skip it first. Display reason and pause time.
4. Display a pause warning before booking using doctor details, and after booking
   using returned queueState. Keep Patients Ahead, replace wait with Queue paused.
   Missing state means unknown; null estimate is not zero.
5. Refresh visible status on entry, app resume and user refresh. No push/socket
   notifications were introduced. Resume does not call the next patient itself.
6. Keep existing login, booking `{doctorId}`, queue states and ambulance flows.
   The ML service request schema is unchanged; no ML teammate deployment is needed.

## Verification performed

Local Express HTTP checks against isolated temporary Atlas records covered 46
request assertions plus simultaneous feedback submissions, repeated pause/resume,
three pause/Call Next races and a double Call Next race. Checked roles/ownership,
input errors, private history, date pagination, legacy unpaused behavior, booking
while paused, null estimates, directory/dashboard exposure, completion and skipping.
Temporary verification records were removed. These checks do not verify deployed
web/mobile UI or production deployment.
